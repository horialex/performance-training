Response time by request

Mean against 95th percentile, sorted slowest first. The gap between the two bars is the tail: where it is wide, a minority of users had a far worse experience than the average suggests.

Average 95% line 3 s orientation mark

The whole browse chain — homepage, category, sub-category, product page — sits above 4.5 s on average and 8.9 s at p95. Every AJAX endpoint stays under 250 ms. The client has set no response-time target, so the 3 s mark is only a common orientation threshold, not a pass/fail line.

Request volume and throughput

Sample count per request, with the throughput it corresponds to. The two are one measurement: every request ran for the same ~3,890 s window, so throughput is sample count divided by that window. They share a chart because a second one would repeat this shape exactly.

Volume follows the flow mix set in the plan — browse 50%, search 30%, add-to-cart 20%, update cart 7%. Throughput carries no independent signal within a single run; it becomes the metric to watch when runs 1–4 are compared, where it shows whether the server absorbed the extra threads or saturated.

Where the load meets the latency

Throughput against 95th-percentile response time. Requests toward the top right are both heavily used and slow — they set what most users actually feel, and they are where tuning pays back most.

Browse chain Other requests

Search autocomplete is the counter-example: the second-highest volume in the run at 1.35 req/s, yet a p95 of 3.1 s and a median of 99 ms. The server is not short of capacity for light requests — the cost is concentrated in full page renders and their assets.

Reading the run

The homepage is the bottleneck, and its assets are why

At 10.0 s average and 13.9 s p95 it is roughly twice as slow as the next request. It also pulls 2,439 KB/s — more received traffic than every other request combined. The rest of the plan sits in the tens of KB/s.

The plan downloads embedded resources with a 6-thread pool, so a homepage sample times the HTML plus its images, CSS and JS. With no CDN in front of the shop, all of that is served by the same host under load. Static-asset delivery is the highest-leverage thing to change before re-testing.

The browse chain degrades as a block

Category (4.86 s), sub-category (4.52 s) and product details (4.88 s) are almost indistinguishable in both average and p95, and each lands near 9 s at p95. They share a rendering path, so they are likely to respond to one fix rather than three separate ones.

Correctness held; only speed degraded

The overall error rate is 0.45%, peaking at 1.09% on product details. At 50 threads the application does not break — it slows down. That distinction shapes the next step: 50 users is below the breaking point, so the stress run still has to find it.

AJAX endpoints are healthy

Ajax update cart (78 ms), cart refresh (111 ms), Ajax add to cart (127 ms) and view cart (235 ms) are all fast, three of the four with a p95 at or below 200 ms. Application logic and database access are not the constraint at this load level.
